什么是 MattPocock Skills？我该怎么用？

MattPocock Skills 是 TypeScript 专家 Matt Pocock 在 GitHub 上公开维护的一组「AI 提示词技能包」，按使用频率与重要度分为三个层级，共 29 个 Skills，可直接安装到 Trae / Cursor / Claude Code 等支持 Skill 协议的 AI IDE 中。本课题汇集了对这套 Skills 的中文版分析报告、选型指南与已装状态对照表。
核心结论（共 6 条）
  1. 三层分级：29 个 Skills 按「必备 → 推荐 → 可选」三层组织，必备层覆盖大部分日常工作流。
  2. 每个 Skill 是一段 YAML 描述的提示词模板：定义了触发条件、提示词内容与期望输出格式，不是代码包。
  3. 兼容主流 AI IDE：Trae、Cursor、Claude Code、Cline、Continue 等支持 MCP/Skill 协议的 IDE 都能装。
  4. 选型原则：先装必备层（覆盖 80% 场景），再按个人工作流需求选推荐/可选层；不要一次性全装。
  5. 安装方式：从官方仓库 clone 或下载 SKILL.md 文件放入 IDE 的 skill 目录即可生效。
  6. 已装状态对照：用户文档显示已装了部分 Skills（详见对照表），未装部分主要是低频场景的辅助技能。

一、这套东西到底是什么

先纠正一个常见误解：它不是提示词模板集合，是给 AI 定的工作流程纪律（SOP）。

作者 Matt Pocock（TypeScript 教育者）在 README 里明确说了他做这套东西要解决的四个失败模式，以及他反对什么：

失败模式 他的诊断 对应解法
Agent 没做我想要的东西 你和 agent 之间有沟通缺口 grilling（开始干活前先被追问）
Agent 太啰嗦 你和 agent 没有统一词汇 shared language / CONTEXT.md
代码跑不起来 没有反馈回路，agent 在盲飞 tdd（红-绿-重构）
做成了泥球 只关心"做出来"，不关心设计 deep modules 系列

他特意点名反对 GSD、BMAD、Spec-Kit 这类方法："它们在接管流程的同时，也拿走了你的控制权"。他的主张是 skills 要小、能改、能组合，你可以 hack 成自己的。

两类 skill，区别很重要

  • User-invoked（你输入 /名字 才触发）：负责编排
  • Model-invoked（agent 判断任务匹配时自动触发）：负责纪律

前者可以调后者，但前者不能调前者。所以 grill-me 只是个两行入口，真正干活的是引擎 grilling——这个结构对你后面理解"为什么你的 grill-me 没生效"很关键。

第 3 优先：`wayfinder`（你有 GitHub，正好用得上）

它解决的是"一个会话装不下的大工程"。你现在的状态就是这个形状：文明6 1 到 20、汉化、英雄无敌X、一堆 skill 工程——每个都是雾里看花，看不到从这到那的路。

它的做法：
- 在 GitHub Issues 上建一张地图（一个带 wayfinder:map 标签的 issue）
- 下面挂决策票（不是任务票——每张票解决一个"需要决定"的问题）
- 每次会话只解决一张票，把答案写进 resolution comment 然后关掉
- 地图有个 "Not yet specified" 区，专门放"你感觉以后会来、但现在还说不清"的事

最关键的一条纪律："每个 session 绝不要 resolve 超过一个 ticket"。这直接治你"用超大提示词一次性砸过去、然后崩掉重来"的模式。

作者明说这个 map 是领域无关的：engineering work、course content，任何符合这个形状的事都行。你做 mod 工程完全适用。

第 4 优先：`teach`

你在一堆提问里说过 "我没有任何的代码基础，需要你简介"。teach 就是为这个场景设计的：

  • 它把当前目录当成一个持续存在的教室，跨 session 记住你的进度
  • MISSION.md 记录你为什么要学这个（先问你，不理解动机就不开课）
  • lessons/0001-xxx.html 是一个个很短、做得很漂亮、可打印的单页课件
  • learning-records/ 记你学到了什么、哪些要回头修
  • 内置了真实的学习科学：提取练习、间隔重复、交错练习，明确区分" fluency（当下能想起来）"和"storage strength（长期记得住）"，目标是后者

学 Lua 的 event 注册机制、学 modinfo 的结构、学 SQLite——都用这个，比每次从头问强得多。

第 5 优先：`prototype`

回答"这个 UI 到底该长什么样"时，它不写代码进项目，而是产出一个你可以直接在浏览器打开的单文件 HTML，或者几个风格迥异的 UI 变体让你挑。你做科技树图标、UI 改版时特别顺手。

第 6：`to-questionnaire` / `ask-matt`

  • 遇到你自己答不了、只有别人能答的决定（比如某个 mod 的原作者为什么这么写），它把问题做成一份问卷，还会追问你"发给谁、你想拿回什么"。
  • ask-matt 是路由器，等你装到十几个 skill 以后，直接问它"这种情况该用哪个"就行。

新旧引擎差在哪

旧版（grill me V，你现在在跑的）：

"Ask the questions one at a time."

新版（grilling，没跑起来的）：

把决策映射成一棵 design tree。按轮推进，frontier = 前置条件已敲定、现在就能问的那些问题。一轮里把整条 frontier 全问完，编号 + 给推荐答案，然后等回答。

还有一条新版独有的硬规矩，价值极高：

寻找 facts 是你的工作，绝不是用户的。 当问题需要环境里的事实（文件系统、工具能查到的），派 sub-agent 去查——不要问用户任何你自己能查到的东西。

对你这种"分析 20 个 mod 文件夹"的场景，这一条能省掉大量来回。旧版只有一句软的"如果能查代码库就去查"，没有 sub-agent 派单、也没有"别被它阻塞，先问 frontier 其余部分"这种调度。

另外一个改动，值得你自己决定

你（或之前的某次操作）在新版 grilling 第 6 行加了一句：

持续访谈用户…… 使用AskUserQuestion工具进行提问。

这和上游设计有张力。上游的问题格式是纯文本的：

❓ **Q1** - **<问题标题>**：<问题正文，可能有多段，包括多个选项>

➡️ <你的推荐答案>

而 AskUserQuestion 是选择题控件（一次最多 4 个问题、每题 2-4 个预设选项）。走控件的话：一轮问不完 frontier、每个问题都被压缩成预设选项、"➡️ 推荐答案"这种开放式建议也没地方放。

两种各有好坏：选择题对不用打字的人更省力，但会丢掉开放式的推荐答案和"一轮问完整条 frontier"的并行效率。建议你两种都试一次再定，别默认就用控件。

二、skill 到底是什么（通俗版）

skill = 一份给 AI 看的操作手册。

平时你跟 AI 说话，它是临场发挥。装了 skill 之后，AI 在合适的时候会自动（或你点名之后）翻开这份手册，按上面的步骤走。

一个 skill 就是一个文件夹，核心是一个 SKILL.md 文件，开头几行写明「我叫什么、什么时候该用我」，下面是具体步骤。

两种触发方式：
- 用户调用：你打 /grill-me 这样的斜杠命令才启动。
- 模型调用：AI 自己判断该用就用了，不用你喊。

场景 2：写作 —— 这是本仓库的隐藏王牌

三个 skill 构成完整流水线，都在 in-progress 桶里（beta，但能用）：

writing-fragments  →  writing-shape  或  writing-beats
   （探索攒素材）        （成文：直线叙述）  （成文：分支旅程）
  • writing-fragments（探索）：不管结构，先往一个 md 文件里堆素材。金句、片段、半成型的想法、 vignette、牢骚、金句都可以。核心是抓 leading word——一个能撑起全篇的隐喻词。
  • writing-shape（成文·直线）：先定读者已具备哪些概念（grounding），再一段一段往前推。每写一段就问「这段给读者的东西，上一段没给过吗」。
  • writing-beats（成文·分支）：choose-your-own-adventure 风格。每次给 2-3 个候选「下一拍」，你选一个，写那一拍，停。适合散文、叙事、演讲稿。

关键设计：grounding（打地基）。每个概念必须先落地，后面的段落才能依赖它。开头要求太多会把读者劝退，内部打地基太多开头又会淹死在定义里——这个杠杆要跟你确认。

场景 3：生成 / 优化 skill

  • writing-for-agents —— 本仓库最有价值的一个，必装。核心概念：
  • context pointer：skill 的 description 就是指针，措辞决定 AI 多可靠地找到它。
  • leading word（门槛词）：一个紧凑概念，比如 tight（紧的循环）、red（循环变红）。一个词锚定一整片行为，比三句话管用。

五、专项分析：bug 类 skill 对简单游戏 mod 适用吗

结论：**适用，但要换掉它的引擎。整体可用度约 70%。**

diagnosing-bugs 的六阶段：

阶段 内容 Civ6 mod 是否可用
P1 建 feedback loop ❌ 卡住，需替换
P2 复现 + 最小化 ⚠️ 部分可用
P3 生成 3-5 个可证伪假设并排序 ✅ 完全可用，最值钱的部分
P4 插桩，一次只改一个变量，[DEBUG-xxxx] 前缀 ✅ 完全可用
P5 修复 + 回归测试 ⚠️ mod 通常没有 test seam
P6 清理 + 复盘「什么本可以预防」 ✅ 完全可用

P1 为什么会卡住

P1 是整个 skill 的核心（「建对 loop，bug 就修好了 90%」），它列了 10 种构造方式：

  1. 失败的测试 ❌ 没有 test runner
  2. curl / HTTP 脚本 ❌ 没有 dev server
  3. CLI + fixture + diff 已知正确快照 ✅ 对 SQL 极好用
  4. 无头浏览器 ❌ 不能 headless 跑游戏
  5. 重放捕获的 trace ⚠️ Database.log / lua.log 勉强算
  6. 一次性 harness ✅ 用 lua.exe 单独加载 Lua 做语法检查
  7. 属性/模糊测试 ❌
  8. 二分 harness ❌
  9. 差分 loop ✅ 旧版 vs 新版数据库 diff
  10. 人工参与的 bash 脚本 ✅ 最后手段，人进游戏看

前 5 种（主流解法）全废，只剩边角料。 直接照搬会在第一步就撞墙。

更重要的判断：mod 的 bug 不是逻辑 bug

Civ6 mod 的 bug 绝大多数是数据/配置类 bug，特征是游戏不崩溃，只是效果不生效：

  • ModifierType 不存在
  • CollectionType / EffectType 组合不合法
  • RequirementSet 引用了不存在的 Requirement
  • SQL UPDATE 的 WHERE 匹配 0 行
  • XML 标签写错 / 少闭合
  • Lua 里 nil 调用
  • .modinfo 的 LoadOrder 顺序错

对这类 bug，假设驱动调试是杀鸡用牛刀。一个静态校验脚本能在 3 秒内命中 80% 的成因——检查所有 Type 引用是否存在于基础数据库、检查 CollectionType/EffectType 组合是否合法。而跑完 P3 的假设排序要 30 分钟。

推荐方案：分流

先跑「Civ6 校验 loop」（静态检查 + 日志 diff）
   ├─ 命中 → 直接修，结束
   └─ 没命中 → 再进 diagnosing-bugs 的 P3-P6

改造量：很小

做成 diagnosing-civ6-mods：
- 替换 P1 一整节：把 10 种 loop 换成 Civ6 版（sqlite3 打库 + SELECT diff / lua.exe 语法检查 / XML 结构校验 / Database.log diff / 人工进游戏）
- 改 P5 一句话：regression test → 「可重复运行的校验脚本」
- 其余原样

P3 的「3-5 个可证伪假设」对 mod 一样有效。常见假设池：
ModifierType 拼错 / Requirement 未定义 / LoadOrder 顺序 / SQL WHERE 匹配 0 行 / Lua 变量作用域。

六、专项分析：domain 类 skill 能通用化吗

结论：**能，而且比你想象的容易——改动量约 15 行。**

domain-modeling 只做两件事：
1. 维护一份 glossary（CONTEXT.md）
2. 写 ADR（架构决策记录）

它唯一的代码耦合点是这一句：

Cross-reference with code —— 当用户描述某事如何工作时，检查代码是否同意。

其余全部是纯语言工作，跟编程毫无关系。

原版概念 角色扮演 写作 文明6 mod
CONTEXT.md 术语表 世界观设定集 / 人物设定 作品术语表 / 风格指南 Modifier/Type 命名规范

关键判断：通用化后，最大受益场景不是 mod 开发

mod 开发的术语表基本是游戏给定的（Modifier、Requirement、ModifierType），你不太需要重新定义。

而角色扮演和写作的术语完全是你自己造的，最需要一致性维护——长篇叙事里同一个概念换三个名字是致命的。

所以 domain 类通用化后，对你价值排序是：
角色扮演 > 写作 > 文明6 mod

硬约束（这条最有用）

CONTEXT.md 必须完全不包含 implementation details。不要把它当 spec、草稿纸或实现决策的仓库。它只是一份 glossary。

这一条能防止你把设定集写成大杂烩。保留它。

具体改动

  1. 删掉或改为可选的 ADR 一节（原版要求「难以逆转 + 无背景会令人意外 + 真实权衡」三条全中才写，非代码场景基本不写）
  2. 改「Cross-reference with code」一句 → 泛化为「对照已有产物」
  3. 其余原样

需要连带复制：CONTEXT-FORMAT.md、ADR-FORMAT.md
